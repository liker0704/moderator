# Риски и меры по их обходу

## Обзор

Документ описывает основные риски проекта и стратегии их митигации.

## Классификация рисков

### По серьезности
- **Критический** - может остановить проект
- **Высокий** - значительное влияние на функциональность
- **Средний** - умеренное влияние
- **Низкий** - минимальное влияние

### По вероятности
- **Высокая** (>50%) - скорее всего произойдет
- **Средняя** (20-50%) - может произойти
- **Низкая** (<20%) - маловероятно

---

## Критические риски

### R-1: Блокировка Discord аккаунта за нарушение ToS

**Описание**: Использование User Token и прямого подключения к Gateway нарушает Discord Terms of Service. Discord может заблокировать аккаунт.

**Вероятность**: Средняя (30-40%)

**Влияние**: Критическое (потеря всей Discord интеграции)

**Индикаторы**:
- Аккаунт заблокирован
- Gateway возвращает 401 Unauthorized
- Невозможно подключиться с User Token

**Меры митигации**:

1. **Резервные аккаунты**
   - Подготовить 2-3 резервных Discord аккаунта
   - Регулярно проверять их работоспособность
   - Держать токены в секретном хранилище

2. **Минимальная активность**
   - Не использовать для массовых операций
   - Соблюдать rate limits
   - Эмулировать человеческое поведение (delays между сообщениями)

3. **Мониторинг**
   - Алерты при ошибках подключения
   - Логирование всех действий
   - Регулярные проверки /test_connection

4. **План восстановления**
   - Процедура быстрой смены токена
   - Документация для получения нового токена
   - Автоматизация переключения на резервный аккаунт

**Contingency Plan**:
Если аккаунт заблокирован:
1. Немедленно переключиться на резервный аккаунт
2. Получить новый User Token
3. Обновить через /setup_discord
4. Проверить работоспособность
5. Расследовать причину блокировки

**Альтернативы** (если все аккаунты заблокированы):
- Переход на Discord Bot API (потеря функциональности - не видны все сообщения)
- Использование официального Gateway (требует MESSAGE_CONTENT intent - может быть недоступен)
- Прекращение поддержки Discord (только Telegram)

---

### R-2: Изменения в Discord Gateway протоколе

**Описание**: Discord регулярно обновляет API и протокол Gateway. Изменения могут сломать интеграцию.

**Вероятность**: Высокая (60-70% в течение года)

**Влияние**: Высокое (временная потеря Discord интеграции)

**Индикаторы**:
- Gateway не подключается
- Ошибки при Identify
- Сообщения не приходят
- Невалидный client_build_number

**Меры митигации**:

1. **Версионирование**
   - Использовать фиксированную версию Gateway (?v=9)
   - Логировать версию при подключении
   - Хранить историю работающих версий

2. **Мониторинг Discord API**
   - Следить за Discord Developer News
   - Подписаться на GitHub репозитории discord.py, discord.js
   - Мониторить сообщества разработчиков

3. **Гибкая архитектура**
   - Изолировать Discord клиент в отдельный модуль
   - Легко обновляемые параметры (super_properties)
   - Конфигурация через БД/env

4. **Быстрые фиксы**
   - Иметь процедуру обновления super_properties
   - Тестовое окружение для проверки изменений
   - Автоматизация деплоя фиксов

**Contingency Plan**:
1. Обнаружение изменений (через алерты/логи)
2. Анализ что изменилось (community, changelogs)
3. Обновление параметров (super_properties, версия Gateway)
4. Тестирование на staging
5. Деплой в production
6. Мониторинг

**Время на восстановление**: 1-4 часа (при быстрой реакции)

---

### R-3: Потеря данных (отсутствие бэкапов)

**Описание**: По решению заказчика бэкапы БД отсутствуют. Сбой PostgreSQL может привести к потере всех данных.

**Вероятность**: Низкая (5-10%)

**Влияние**: Высокое (потеря истории, настроек, allowlist)

**Индикаторы**:
- PostgreSQL не стартует
- Ошибки чтения/записи в БД
- Corruption данных

**Меры митигации**:

1. **Профилактика**
   - Использовать надежный диск (SSD)
   - Регулярные проверки состояния диска
   - Docker volumes для изоляции
   - Мониторинг здоровья БД

2. **Быстрое восстановление**
   - Процедура инициализации пустой БД
   - Seed скрипты для базовых данных
   - Документация для восстановления настроек

3. **Минимизация влияния**
   - Критичные настройки хранить в .env (allowlist можно восстановить)
   - Логирование важных событий
   - Экспорт данных (опционально, v1.0+)

**Contingency Plan**:
1. Попытка восстановления БД (pg_dump если возможно)
2. Если не удалось - создание новой БД
3. Запуск миграций
4. Настройка Discord заново (/setup_discord)
5. Восстановление allowlist вручную
6. Информирование модератора о потере истории

**Альтернатива**: Внедрить бэкапы (опционально)
- Ежедневный pg_dump
- Хранение 7 дней
- S3 или локальное хранилище

## Высокие риски

### R-4: Превышение бюджета LLM API (v0.2+)

**Описание**: Стоимость запросов к LLM API может превысить ожидаемую.

**Вероятность**: Средняя (30%)

**Влияние**: Среднее (финансовые затраты, необходимость отключения LLM)

**Индикаторы**:
- Стоимость/день > $10
- Много запросов к LLM
- Использование дорогих моделей (GPT-4, Claude Opus)

**Меры митигации**:

1. **Мониторинг стоимости**
   - Логирование каждого запроса к LLM
   - Подсчет tokens (input + output)
   - Ежедневные отчеты стоимости
   - Алерты при превышении лимита

2. **Оптимизация**
   - Использовать более дешевые модели (Sonnet вместо Opus)
   - Кеширование вариантов
   - Ограничение контекста (20 сообщений макс)
   - Сжатие промптов

3. **Лимиты**
   - Максимум N запросов/день
   - Максимум N tokens/запрос
   - Отключение при превышении бюджета

**Contingency Plan**:
1. Алерт при превышении $5/день
2. Анализ причин (много запросов? дорогая модель?)
3. Оптимизация или смена модели
4. Если не помогло - временное отключение LLM
5. Ручные ответы модератором

---

### R-5: Нестабильность соединения с Discord Gateway

**Описание**: Частые обрывы соединения, reconnect не всегда успешен.

**Вероятность**: Средняя (40%)

**Влияние**: Среднее (пропуск сообщений, задержки)

**Индикаторы**:
- Частые reconnects (>10/час)
- Heartbeat ACK не приходит
- Соединение закрывается без причины

**Меры митигации**:

1. **Robust reconnection**
   - Автоматический reconnect
   - Exponential backoff (2, 4, 8, 16... сек)
   - Resume с сохраненным session_id
   - Fallback на полный Identify

2. **Мониторинг**
   - Логирование каждого disconnect/reconnect
   - Алерты при >5 reconnects за 10 мин
   - Отслеживание last_heartbeat

3. **Настройка сети**
   - Стабильное интернет-соединение
   - Использование надежного хостинга
   - Keep-alive для WebSocket

**Contingency Plan**:
1. При частых reconnects - алерт
2. Проверка сети (ping, traceroute)
3. Перезапуск Discord клиента
4. Если не помогает - смена хостинга/сети

---

### R-6: Rate Limiting от Discord API

**Описание**: Превышение rate limits может привести к временной блокировке API.

**Вероятность**: Средняя (30%)

**Влияние**: Среднее (задержки отправки, ошибки постинга)

**Индикаторы**:
- 429 Too Many Requests
- X-RateLimit-Remaining = 0
- Очередь растет

**Меры митигации**:

1. **Уважение лимитов (v0.2+)**
   - Bucket system для каждого route
   - Парсинг X-RateLimit headers
   - Ожидание reset_after
   - Очереди с приоритетами

2. **Оптимизация**
   - Группировка сообщений (если возможно)
   - Избегание лишних запросов
   - Кеширование данных

3. **Fallback**
   - При rate limit - отложить в очередь
   - Повторная попытка после reset

**Contingency Plan**:
1. Получение 429 → wait retry_after
2. Повторная попытка
3. Если часто - увеличить delays
4. Информирование модератора о задержках

## Средние риски

### R-7: Telegram Bot API недоступен

**Описание**: Telegram API временно недоступен (outage, сетевые проблемы).

**Вероятность**: Низкая (10%)

**Влияние**: Среднее (карточки не доставляются, ответы не отправляются)

**Индикаторы**:
- Timeout при getUpdates
- Ошибки sendMessage
- 502/503 от Telegram API

**Меры митигации**:

1. **Retry механизм**
   - Exponential backoff
   - Максимум 5 попыток
   - Логирование ошибок

2. **Мониторинг**
   - Алерты при ошибках Telegram API
   - Проверка статуса Telegram (status.telegram.org)

3. **Очереди**
   - Сообщения в очереди при недоступности
   - Отправка после восстановления

**Contingency Plan**:
1. Обнаружение недоступности
2. Ожидание восстановления (обычно минуты)
3. Retry отправки
4. Алерт модератору если >10 мин

---

### R-8: Недостаточная производительность

**Описание**: Система не справляется с нагрузкой (>500 событий/день).

**Вероятность**: Низкая (15%)

**Влияние**: Среднее (задержки, пропуски сообщений)

**Индикаторы**:
- Latency карточек > 5 сек
- CPU/RAM usage > 90%
- Очереди растут
- БД медленная

**Меры митигации**:

1. **Оптимизация**
   - Индексы БД
   - Оптимизация запросов
   - Кеширование (Redis)
   - Асинхронные операции

2. **Scaling**
   - Увеличить ресурсы (CPU, RAM)
   - Горизонтальное масштабирование воркеров (v0.2+)
   - Оптимизация Docker

3. **Мониторинг**
   - docker stats
   - Метрики производительности
   - Алерты при высокой нагрузке

**Contingency Plan**:
1. Идентификация узкого места (БД? CPU? сеть?)
2. Оптимизация узкого места
3. Увеличение ресурсов
4. Если не помогает - масштабирование

---

### R-9: Безопасность (утечка токенов)

**Описание**: Discord User Token или Telegram Bot Token могут быть скомпрометированы.

**Вероятность**: Низкая (10%)

**Влияние**: Высокое (несанкционированный доступ)

**Индикаторы**:
- Неожиданные действия от бота
- Сообщения, которые модератор не отправлял
- Изменения в настройках

**Меры митигации**:

1. **Защита токенов**
   - Хранение в .env (не в коде)
   - Шифрование User Token в БД (AES-256)
   - chmod 600 на .env
   - Не коммитить .env в git

2. **Мониторинг**
   - Аудит лог всех действий
   - Алерты при подозрительных операциях

3. **Ротация**
   - Процедура смены токенов
   - Регулярная проверка

**Contingency Plan**:
1. Обнаружение компрометации
2. Немедленная смена токенов
3. Анализ аудит-логов
4. Блокировка доступа
5. Расследование причины

---

### R-10: Ошибки в коде (баги)

**Описание**: Критические баги могут привести к потере данных, некорректной работе.

**Вероятность**: Средняя (40%)

**Влияние**: Среднее (некорректные ответы, потеря сообщений)

**Меры митигации**:

1. **Тестирование**
   - Unit тесты
   - Integration тесты
   - Manual тестирование
   - Staging окружение

2. **Code Review**
   - Ревью критических изменений
   - Статический анализ (linters)
   - Type checking (mypy, TypeScript)

3. **Мониторинг**
   - Логирование ошибок
   - Алерты при exceptions
   - Sentry или аналог (опционально)

**Contingency Plan**:
1. Обнаружение бага (через логи/алерты)
2. Локализация проблемы
3. Hotfix
4. Тестирование
5. Деплой
6. Postmortem

## Общая стратегия управления рисками

### 1. Проактивность
- Регулярный мониторинг индикаторов
- Превентивные меры (резервные аккаунты, тесты)
- Подписка на новости Discord/Telegram API

### 2. Быстрая реакция
- Алерты при критических событиях
- Процедуры восстановления
- Hotfix процесс

### 3. Документация
- Runbooks для каждого риска
- Контакты и эскалация
- Postmortem после инцидентов

### 4. Тестирование
- Регулярное тестирование contingency планов
- Chaos engineering (опционально)
- Drills для критических рисков

## Мониторинг и алерты

### Критические алерты (немедленная реакция)
- Discord Gateway не подключается >5 мин
- БД недоступна
- Backend упал
- Утечка токенов

### Высокие алерты (реакция в течение часа)
- Частые reconnects Discord (>10/час)
- Rate limiting Discord
- LLM стоимость >$5/день

### Средние алерты (реакция в течение дня)
- Диск заполнен >80%
- Задержки карточек >5 сек
- Открытые задачи >100

---

## Заключение

Большинство рисков имеют низкую или среднюю вероятность. Критические риски (R-1, R-2, R-3) требуют постоянного мониторинга и готовности к быстрой реакции. Проактивные меры и документированные процедуры восстановления минимизируют влияние рисков.
